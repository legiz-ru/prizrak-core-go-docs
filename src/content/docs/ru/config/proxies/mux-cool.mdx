В Prizrak-Core есть мультиплексирование **mux.cool**, совместимое с Xray. Это тот же протокол, что `mux` в Xray-core: TCP-потоки и UDP/XUDP-сессии идут поверх общих TCP-соединений. Используется реализация из [MetaCubeX/mihomo#2980](https://github.com/MetaCubeX/mihomo/pull/2980). Она расширеннее, чем в Xray-core, но полностью с ним совместима.

- **Клиент.** Включается у прокси отдельно от `smux`. Включать их вместе нельзя.
- **Сервер.** mux.cool от клиентов Xray принимает любой входящий на общем обработчике sing: VLESS и VMess, а также Trojan, Shadowsocks, AnyTLS, TUIC, Hysteria2 и другие, поверх любого транспорта, в том числе XHTTP. Параметр на сервере не нужен. Через XHTTP сервер может не давать CDN обрывать простаивающее скачивание, см. `mux-keep-alive-secs` на странице [XHTTP](/ru/config/proxies/xhttp/#листенер-регулятор-настройки-http2-и-keepalive-для-muxcool).
- **XUDP.** Отдельные UDP-сессии с управлением их количеством и политикой для UDP/443.
- **Ограничение соединений.** Можно ограничить, сколько TCP-соединений открывается всего, сколько сессий идёт по каждому одновременно и сколько сессий соединение проводит за время жизни. Потом соединение заменяется новым.

```yaml
proxies:
  - name: vless-mux
    type: vless
    # ...
    mux.cool:
      enabled: true
      # max-carriers: 0           # максимум TCP-соединений, 0 — без ограничения
      # max-concurrency: 8        # активных сессий на одно соединение
      # max-connections: 128      # сессий за время жизни соединения до ротации
      # xudp-concurrency: 0       # отдельных XUDP-сессий на соединение, 0 — общий пул
      # xudp-proxy-udp443: reject # reject | allow | skip — что делать с UDP/443
```

`xudp-proxy-udp443` решает, что делать с UDP-потоками на порт 443 (QUIC):

- `reject` (по умолчанию): поток отклоняется с ошибкой, как в Xray;
- `allow`: поток идёт через mux.cool, как остальной UDP;
- `skip`: поток идёт мимо mux.cool, через собственный UDP прокси.

Параметр уровня прокси [`udp-443: reject`](/ru/config/proxies/udp-443/) проверяется раньше mux.cool.

Включить mux.cool для пользователей подписки Remnawave можно через маппер хоста Remnawave, см. [mux.cool через маппер хоста](/ru/remnawave/mux-cool/).

## Сервер

Если цель потока читает медленнее, чем приходят данные, сервер перестаёт читать соединение, пока цель их не заберёт, как и Xray: TCP-поток не должен терять данные. Остальные потоки этого соединения в это время тоже ждут. Если цель ничего не забирает 300 с (`connIdle` в политике Xray по умолчанию), её поток закрывается с ошибкой, и соединение работает дальше. Потоков, для которых данных нет, это ограничение не касается.

## XDRIVE

Прокси [XDRIVE](/ru/config/proxies/xdrive/) без mux.cool не работает. Одно соединение mux.cool — это одна сессия XDRIVE со своими объектами на хранилище и своим опросом, поэтому как можно больше потоков должны делить её между собой.

- Обязателен `enabled: true`, а `xudp-proxy-udp443: skip` запрещён. Иначе конфиг не загрузится.
- `max-concurrency` ниже 128, в том числе значение по умолчанию 8, поднимается до 128. Большее значение остаётся как есть.
- `max-connections` ниже 1024, в том числе значение по умолчанию 128, поднимается до 1024: столько потоков Xray-core пропускает через одно соединение mux. Большее значение остаётся как есть. После стольких потоков за свою жизнь сессия заменяется новой.
- `max-carriers` ограничивает, сколько сессий открыто одновременно, а значит и число запросов к хранилищу.
- На запуск новой сессии отводится до 60 с, и потоки, которым она нужна, ждут её столько же, а не 5 с, как при обычном подключении.

:::note[Сервер VLESS]
До v1.19.33-r8 входящий VLESS обслуживал mux.cool более простым сервером из sing-vmess, эта реализация работала только для VMess. В более новых релизах VLESS тоже использует её, с её обработкой XUDP и ограничениями.
:::
